Week 1 · Day 1
The 7-Step Troubleshooting Methodology
Follow this every time — don't guess, diagnose.
1
Identify the Problem Ask: What happened? What error? What changed recently? Don't touch anything yet.
2
Theory of Probable Cause Start with the simplest explanation first. Is the cable plugged in?
3
Test the Theory Try your fix. Works? Move on. Fails? Form a new theory.
4
Plan of Action Know what you'll do, what could break, and how to reverse it.
5
Implement the Solution Carry out your plan carefully and methodically.
6
Verify Full Functionality Confirm your fix worked AND nothing else broke.
7
Document Everything Write the problem, cause, and fix. This is the most skipped step — don't skip it.
💡 The best IT engineers aren't those who know the most answers — they're the ones who ask the best questions first.

Week 6 · Day 2
DNS — How Names Become IPs
The phone book of the internet. Every website visit uses DNS.

DNS Resolution Flow

1
Check hosts file /etc/hosts — if the name is here, use it. No DNS needed.
2
Check local cache Already looked this up recently? Use the cached answer.
3
Query DNS resolver Your configured DNS server (from DHCP or manual config).
4
Resolver asks Root NS Roots direct to .com, .org, .uk TLD servers.
5
TLD → Authoritative NS Google's own nameservers return the IP. Cached and returned.

DNS Record Types

A
Address — maps hostname → IPv4.
www → 93.184.216.34
AAAA
Quad-A — maps hostname → IPv6
CNAME
Alias — points one name to another.
mail.co → co.com
MX
Mail Exchanger — which server handles email for this domain
PTR
Reverse DNS — IP → hostname. Used by mail servers to verify senders.
TTL
Time To Live — how long resolvers cache this record (in seconds). Lower before IP changes!
# Test DNS from command line
dig google.com A # Linux/macOS
nslookup google.com # Windows
dig @8.8.8.8 google.com # Query specific server

Week 4 · Day 1
Linux Filesystem Hierarchy
Every Linux system looks the same — because of the FHS standard. Know where everything lives.

Key Directories

/etc
⭐ Most important. All system config files. nginx → /etc/nginx/. SSH → /etc/ssh/sshd_config
/var/log
All log files. syslog, auth.log, nginx/access.log. Check here when things break.
/home
User home directories. /home/alice, /home/bob. Your personal files live here.
/tmp
Temporary files — cleared on reboot. Safe to use for scratch files.
/usr/bin
User programs: ls, cat, grep, python3, nginx, git. Your PATH points here.
/proc
Virtual filesystem. /proc/cpuinfo, /proc/meminfo — live kernel data. Not real files.

Active Directory Architecture
The brain of every Windows enterprise network

How AD is Structured

FOREST: company.com  (top level)
└── DOMAIN: company.com
├── DC01, DC02 (Domain Controllers)
├── OU: London
├── Users: Alice, Bob
└── Computers: LDN-PC-001
├── OU: Manchester
└── OU: Servers
💡 OUs (Organisational Units) are folders for AD objects. You link Group Policies to OUs to apply settings to all objects inside.

AGDLP — The Permissions Model

Never assign permissions directly to user accounts. Use groups.

A

↓ add to

↓ nested into

✅ To give Alice access: add her to GG_Finance_Staff. That's it — one action, permissions flow automatically.

Week 9 · Day 2
Docker Core Concepts
📄

Dockerfile

A recipe. Text file with instructions to build an image.

FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]
🖼️

Image

A read-only template built from a Dockerfile. Like a class in code.

# Build image
docker build -t myapp:v1 .

# List images
docker images

# Pull from Docker Hub
docker pull nginx:latest
📦

Container

A running instance of an image. Like an object from a class.

# Run a container
docker run -d -p 80:80 \
  --name web nginx

# Shell into it
docker exec -it web bash

# See logs
docker logs -f web

Week 8 · Day 1
Cloud Service Models
How much YOU manage vs how much the cloud provider manages

🏗️ IaaS

Infrastructure as a Service

Your App ← YOU manage
OS ← YOU manage
VM / Compute ← AWS
Physical HW ← AWS

Examples: EC2, Azure VMs. Most control, most responsibility.

🔧 PaaS

Platform as a Service

Your App ← YOU manage
Runtime ← Provider
OS ← Provider
Hardware ← Provider

Examples: Elastic Beanstalk, Azure App Service, Heroku.

☁️ SaaS

Software as a Service

Application ← Provider
Runtime ← Provider
OS ← Provider
Hardware ← Provider

Examples: Gmail, Office 365, Salesforce. Just use it.

Week 8 · Day 2–3
AWS Core Services

Essential Services Map

EC2
Virtual Machines. Choose instance type (CPU/RAM), OS image (AMI), storage. Pay per second.
S3
Object Storage. Store any file. 11 nines durability. Pay per GB. Hosts static websites.
VPC
Your Private Network. Subnets, route tables, internet gateway. Your network in the cloud.
IAM
Identity & Access. Users, groups, roles, policies. Who can do what.
RDS
Managed Databases. MySQL, PostgreSQL. Automatic backups, patching, Multi-AZ failover.
Lambda
Serverless Functions. Run code in response to events. Pay only for execution time.
CloudTrail
Audit Log. Every API call recorded. Essential for security investigations.

AWS Shared Responsibility Model

☁️ AWS is responsible FOR the cloud
Physical data centres · Hardware · Hypervisor · Network infrastructure · Managed service infrastructure
🔐 YOU are responsible IN the cloud
OS configuration · Application code · Data encryption · IAM policies · Security Groups · Network ACLs
⚠️ A misconfigured S3 bucket exposing private data is YOUR fault — not AWS's. AWS provides the secure infrastructure; you are responsible for configuring it correctly.
🔑 Never commit AWS access keys to GitHub. Automated scanners find them within minutes and will use them to run up huge bills.

Week 11 · Day 1
The CIA Triad
Every security decision maps back to one of these three principles
🔒
Confidentiality
Only authorised people can read the data
Controls: Encryption, MFA, access controls, least privilege

Violated by: Data breaches, eavesdropping, exposed API keys
✅
Integrity
Data has not been tampered with or altered
Controls: Hashing, digital signatures, audit logs, version control

Violated by: Man-in-the-middle attacks, file corruption, unauthorised edits
⏱️
Availability
Systems are accessible when legitimate users need them
Controls: Redundancy, backups, load balancing, DDoS protection

Violated by: DDoS attacks, ransomware, hardware failures
Week 11 · Day 2
Encryption & Hashing

Symmetric vs Asymmetric Encryption

Symmetric (AES) Asymmetric (RSA)
Keys Same key encrypts + decrypts Public key encrypts, private key decrypts
Speed Fast ✅ Slow ⚠️
Problem How to share the key? No key sharing needed
Used for BitLocker, file encryption, VPN data HTTPS handshake, SSH keys, email signing
🤝 TLS (HTTPS) uses both: Asymmetric to securely exchange a key, then symmetric for the actual data — best of both worlds.

Hashing — One-Way Fingerprints

A hash takes any input and produces a fixed-size output. You cannot reverse it — and the same input always produces the same hash.

# SHA-256 of "password"
"password" → 5e884898da28047151d0e56f8dc6292773603d0d6aabbdd62a11ef721d1542d8

# Even one character different = completely different hash
"Password" → 8be3c943b1609fffbfc51aad666d0a04adf83c9d29d7d9f8ea9f4ef7b55cdb9
Passwords
Stored as hashes — never plain text. bcrypt adds a "salt" to prevent rainbow table attacks.
File integrity
Compare SHA-256 of downloaded file vs published hash — any tampering changes the hash.
MD5
Broken for security — still used for non-security checksums only.

Backup, DR & Monitoring

3-2-1-1-0 Rule · RTO · RPO · Backup Types

Week 10 · Day 5
Backup Strategy

The 3-2-1-1-0 Backup Rule

3
Copies of your data — original + 2 backups
2
Different media — e.g. local disk AND cloud
1
Off-site copy — fire or flood can't destroy all copies
1
Immutable backup — ransomware can't encrypt or delete it
0
Errors after verification — test your restores! Untested backups aren't backups.

RTO vs RPO

DISASTER STRIKES
SERVICE RESTORED
← RTO: Max downtime →
RTO
Recovery Time Objective — maximum acceptable downtime. "We must be back online within 4 hours." Drives redundancy architecture.
RPO
Recovery Point Objective — maximum data loss in time. "We cannot lose more than 1 hour of data." Drives backup frequency.
💡 If RTO = 1 hour, you need automated failover. If RPO = 15 minutes, you need continuous replication. These business requirements drive your infrastructure design.
